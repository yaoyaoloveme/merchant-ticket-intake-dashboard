# 每日新增工单分析看板

读取现有 Forge 同步看板的只读工单列表，建立本地 SQLite 分析库，提供：

- 每日新增工单趋势与分类拆分
- 当日相对前一日、近 7 日均值的类型增量
- 增长异常、处理异常、数据质量异常和高风险描述
- 问题描述主题归类及原文样例
- KA 商家反馈：按多付/漏付、批量核实、回访工单、介入问题分类，逐品牌展开到具体工单
- 服务运行期间每 5 分钟自动同步当天和前一天工单；页面会在同步完成后自动更新
- 高风险雷达单独展示可定位的具体工单和命中依据；运营异常雷达保留增长、处理与数据质量问题

## 使用

最简单的启动方式：双击 `启动看板.command`，浏览器会自动打开。

首次手动同步近 14 天：

```bash
/opt/homebrew/bin/python3 app.py --sync --days 14
```

统一工作台：<http://127.0.0.1:8090>

每日新增工单分析：<http://127.0.0.1:8090/daily>

员工工单卡点看板：<http://127.0.0.1:8090/employee-dashboard>

日报中心：<http://127.0.0.1:8090/#reports>

- 每天 18:00、23:59 的双看板定时分析生成后，会从本机私有归档目录自动进入日报中心。
- 正式日报按日期保留两个版本，支持网页阅读、截图查看和原始分析数据下载；手动验证目录不会展示。
- 本机日报中心保留完整报告、截图和原始数据；GitHub Pages 日报中心只发布白名单汇总指标，不上传员工姓名、逐单原文、截图或内网链接。

派单工作台：<http://127.0.0.1:8090/dispatch>

仅同步数据：

```bash
/opt/homebrew/bin/python3 app.py --sync --days 14 --no-server
```

如源看板地址变化，可设置环境变量 `TICKET_DASHBOARD_URL`。

## 客诉稽查实时分析

独立页面：<http://127.0.0.1:8090/complaint-audit>

- 默认展示本月，支持近6个月、日/周趋势、责任分布、正式根因拆解、客服排名、逐单明细和字段变更历史。
- 以唯一稽查单ID统计；仅“已稽查”进入范围，仅“审核通过”进入正式成立/不成立数字。
- 责任只读取上游正式责任主体或配置的原因节点ID映射，缺失时显示“责任待确认”。
- 接口模式下每60秒检查增量，页面每10秒检查本地数据版本；首次回溯近6个月，每日核对本月和上月。
- 该页面及其数据不会进入 `docs/` GitHub公开快照。

首次使用双击 `配置客诉看板.command`，设置统一访问口令并安装Mac登录自动启动服务。口令哈希和会话密钥保存在 `~/.config/daily-ticket-dashboard/complaint-audit.env`，不写入仓库。

Forge上游需要按 [接口契约](contracts/forge_complaint_audits_api.md) 部署两个只读接口。接口未部署期间，可在私有环境中设置 `COMPLAINT_AUDIT_SOURCE_MODE=excel`，然后从页面导入Forge导出的 `.xlsx` 文件。Excel模式使用正式原因分类路径分析责任和根因；由于当前导出缺少独立的稽查完成时间、稽查结论和原因节点ID，月份暂按“完成处理时间”归属，缺失字段保持未填写，不做推断。

## 统计口径

- 每日新增：按工单的创建时间归日，一张工单只计一次。
- 当分析日期为今天时：今天、前一日和近 7 日历史均截取到当前时刻再比较，避免“今天未结束”与“昨日全天”直接比较。
- 类型增长：默认对比前一日，同时展示近 7 日均值。
- 增长异常：当日数量至少达到 10 单，且高于近 7 日均值 `max(5单, 2个标准差)`。
- KA 工单：店铺能够匹配到 Forge 的 KA 店铺品牌，即源列表品牌字段非空。
- 记录异常：缺少关键字段、长时间待领取/未稽查、响应过慢、同店同描述重复或命中高风险描述。
- 问题主题：基于描述关键词做可解释归类，不代替人工责任判定。
- 高风险雷达：仅识别有明确语境的暴力、人身安全、情绪冲突升级、舆情曝光、监管举报、报警、未成年人、食品安全、现金/财产、连续盗窃和隐私风险。普通“曝光”“举报”“异常”“投诉”等词不单独升级为高风险。

本项目只读取现有看板，不调用其刷新接口，也不修改源系统数据。“实时”受上游源看板数据刷新频率限制。

## 本机天润派单工作台（过渡版）

- 派单已从分析看板拆出，仅在独立页面 `/dispatch` 提供天润 Cookie 连接检测、待领取值守工单池、16名组员勾选、批量分派预览和操作台账。
- 管理接口只接受 `127.0.0.1` / `::1` 的本机请求；该板块不会出现在 GitHub Pages 公开版。
- Cookie 保存到被 Git 忽略的 `data/tianrun_cookie.txt`，文件权限为仅当前用户读写；页面和接口不会回显 Cookie 原文。
- 必须使用重新登录后取得的 Cookie。若天润返回登录失效，系统停止提交，更新 Cookie 后重新预览。
- 工单池实时读取当前处理队列为“值守客服问题处理组”、状态为“待领取/待接单”的全部开放工单；实时读取失败时保留最近一次本地同步结果并明确提示。
- 组员名单固定展示为复选框，选择多名员工时按工单池当前顺序轮询均分，预览会逐单列出接收人。
- 默认只允许预览，真实分派关闭。完成生产验证并明确批准后，以环境变量 `TIANRUN_ASSIGN_ENABLED=1` 启动看板才会开放“执行真实分派”按钮。
- 分派中心支持类型、等待时长、风险、KA 和关键词筛选；当天记住手动勾选的当班人员，按今日通过本看板提交的总量及类型数量均衡推荐（不代表天润全量在手量）。预览可逐单调整接收人，更新方案后只需点击一次“确认并执行分派”。
- 后台逐单提交并持久记录台账，`batchAssign` 受理只记录为“已提交待核验”。通过现有源工单库的处理人逐单核验，源库同步可能延迟，查不到不判失败；网络中断记录为“提交结果待确认”，禁止重复分派，仅明确失败和未提交的工单可重新生成方案。每5分钟刷新与核验，真实生产写入不参与开发测试。
- 当前没有天润详情直连核验能力；现有自动核验依据源工单库处理人，不能替代天润详情。未接入排班，勾选人员仅代表操作人手动指定的当班名单，未自动执行定时分派。

## 公开版部署

- 独立仓库：https://github.com/yaoyaoloveme/merchant-ticket-intake-dashboard
- 公开地址：https://yaoyaoloveme.github.io/merchant-ticket-intake-dashboard/
- `docs/` 是只读公开版：根页面为统一工作台，站内整合每日新增看板、员工卡点看板入口和脱敏日报中心；每日新增页继续保留四类工单分析、KA逐单明细、高风险雷达、根因搜索与分页。
- `publish_snapshot.py --sync --push` 从内网同步今天和昨天、更新逐单证据，再生成公开快照、提交并推送。GitHub Actions 将 `docs/` 部署到 Pages。
- Mac 登录后由 `com.codex.merchant-ticket-pages-publisher` 定时任务每300秒运行；支持重启后恢复，同一时刻只运行一个发布任务。
- 浏览器每30秒检查快照版本，有新版本即刷新。GitHub部署与缓存可能带来额外延迟，不保证严格的300秒端到端延迟。
- 必须保持采集电脑开机、联网且能访问内网。电脑休眠、内网不可达或推送失败时，公网仍显示最后成功快照；源数据超过10分钟未更新会显示过期提示。
- GitHub无法直接抓取私网地址。要脱离本机持续采集，须将发布任务迁移到具备内网访问能力的常驻服务器。
- 发布JSON保留业务问题、工单/店铺编号和品牌；基础脱敏手机号、证件号、邮箱及显式联系方式，处理人仅显示是否分配。自由文本脱敏并非完整的人工隐私审核。
- SQLite、凭据与本机运行日志不提交。源系统链接仅供有内网权限的人使用，不影响页面内查看具体工单。

手动生成快照（不推送）：

```bash
/opt/homebrew/bin/python3.14 publish_snapshot.py
```

发布日志：`~/Library/Logs/merchant-ticket-pages-publisher.log`。
